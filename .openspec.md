# OpenSpec: Sistema Nacional de Notificación ESAVI - Frontend

## 1. Identidad del Proyecto
* **Nombre:** Plataforma ESAVI (Eventos Supuestamente Atribuibles a la Vacunación o Inmunización).
* **Entidades:** Superintendencia de Regulación Sanitaria (SRS), MINSAL, ISSS.
* **Objetivo:** Registro, seguimiento y dictamen de casos ESAVI mediante un flujo de 6 fases y cumplimiento estricto del POE de Investigación.

## 2. Stack Tecnológico
* **Core:** React 18 + TypeScript.
* **Build Tool:** Vite.
* **Enrutamiento:** React Router DOM v6 (Usando `<HashRouter>` para compatibilidad con GitHub Pages).
* **Gestor de Estado Global:** Zustand (Ej: `useAuthStore`, `useCasesStore`).
* **UI Framework:** Material-UI (MUI) v6.
* **Manejo de Formularios:** React Hook Form + Zod (`@hookform/resolvers/zod`).
* **Exportación de Documentos:** `react-to-print`.

## 3. Reglas Estrictas de Código (¡No Improvisar!)
* **MUI v6:** 
  * NO usar `InputProps` en `TextField`, usar la nueva sintaxis `slotProps={{ input: { startAdornment: ... } }}`.
  * NO usar atributos de texto sueltos como `fontWeight="bold"` directamente en componentes, usar siempre `sx={{ fontWeight: 'bold' }}`.
* **Zod + React Hook Form:** 
  * Para inputs numéricos (ej. Edad), usar `z.union([z.string(), z.number()]).transform((val) => Number(val))` para evitar errores de inferencia de tipos entre Zod y RHF.
* **Componentes Funcionales:** Usar siempre funciones tradicionales exportadas por defecto: `export default function ComponentName() {}`. Evitar `const ComponentName = () => {}`.

## 4. Control de Acceso Basado en Roles (RBAC)
El sistema renderiza UI dinámicamente según el rol en `useAuthStore`.
* `ESAVI_LOCAL`: Médico Clínico en punto de atención.
* `INMUNO_LOCAL`: Personal de enfermería / Puesto de vacunación.
* `EPIDEMIO_LOCAL`: Epidemiólogo local o de campo (SIBASI).
* `ESAVI_INSTITUCIONAL`: Referente general a nivel central (SRS/MINSAL).
* `INMUNO_INSTITUCIONAL`: Jefatura de Inmunizaciones.
* `EPIDEMIO_INSTITUCIONAL`: Epidemiología Nivel Central.
* `SECRETARIADO`: Secretariado Técnico (audita y aprueba el pase a comité).
* `COMITE_EXTERNO`: Comité Independiente (emite dictamen final de causalidad).

## 5. Arquitectura de Carpetas
* `/src/components`: Componentes reutilizables (layout, modales genéricos, protección de rutas).
* `/src/features/auth`: Lógica y UI de Login.
* `/src/features/cases`: Dashboards, listados, detalle del caso y `GestorEvidencias.tsx`.
* `/src/features/comittee`: Vistas exclusivas del comité (Dictamen, Cierre).
* `/src/features/forms`: Subdividido por las fases operativas.
* `/src/store`: Tiendas de Zustand.

## 6. Flujo Operativo y Ciclo de Vida del Caso (Máquina de Estados)
### Fase 1: Notificación (Apertura)
* **Objetivo:** Registro primario del evento.
* **Estado Backend:** `NUEVO` o `NOTIFICADO`.
* **Regla:** Se debe evaluar inmediatamente si cumple con los criterios de Gravedad.

### Fase 2: Evaluación (Triaje y Matriz de Riesgo)
* **Objetivo:** Calcular la gravedad y determinar el nivel de respuesta.
* **Estado Backend:** `EN_EVALUACION`.
* **Regla (Niveles de Respuesta):** Crítico (Nacional), Alto (Regional), Medio (Departamental), Bajo (Local).

### Fase 3: Asignación (Despliegue del ERR)
* **Objetivo:** Designar al Equipo de Respuesta Rápida (ERR).
* **Estado Backend:** `ASIGNADO_A_ERR`.

### Fase 4: Investigación de Campo (Llenado de Anexos)
* **Objetivo:** Recolección de evidencias mediante submódulos.
* **Estado Backend:** `EN_INVESTIGACION`.
* **Regla:** El Anexo III (Logística) debe validarse primero.

### Fase 5: Control de Calidad
* **Objetivo:** Auditoría de la investigación de campo por el Secretariado.
* **Estado Backend:** `EN_REVISION_SECRETARIADO`.
* **Bucle de rechazo:** Si hay error, cambia a `DEVUELTO_A_INSTITUCIONAL`. Si es correcto, avanza a `APROBADO_PARA_COMITE`.

### Fase 6: Cierre y Dictamen de Causalidad
* **Objetivo:** Resolución técnica médica y legal.
* **Estado Backend:** `CERRADO_DICTAMINADO`.

## 7. Reglas de Negocio Estrictas (Manual SRS)
* **Repositorio Digital (Anexo I):** Carpetas obligatorias: 1. Clínica, 2. PNI, 3. Epidemiológica, 4. General.
* **Anexo III (Logística):** Frontend exige validación de 7 puntos antes del trabajo de campo.
* **Anexo V (Puesto de Vacunación):** Observación física (cadena de frío, anafilaxia) y guía de entrevista al vacunador.
* **Anexo VI (Domicilio y Comunidad):** 3 fases: 1. Observación comunitaria, 2. Entrevista domiciliaria, 3. Cierre/Devolución.
* **Anexo VII (Evaluación Clínica):** Si es mujer (12 a 50 años), desplegar campos obstétricos.

## 8. Matriz de Responsabilidades y Flujo de Notificaciones (CRUD por Rol y Fase)
El backend y frontend deben habilitar permisos de **ESCRITURA** y desencadenar **NOTIFICACIONES** estrictamente de esta manera:

* **Fase 1 (Notificación y Apertura):** 
  * **Acción:** `ESAVI_INSTITUCIONAL` llena la Notificación Inicial y envía el Formulario de Apertura.
  * **Notificación:** Al enviarse, el `SECRETARIADO` recibe una alerta en el sistema indicando que un nuevo caso ha sido aperturado.
* **Fase 2 (Evaluación de Riesgo):**
  * **Agendamiento:** `ESAVI_INSTITUCIONAL` convoca una reunión (creando la agenda dentro del sistema) con el Equipo Coordinador (`INMUNO_INSTITUCIONAL` y `EPIDEMIO_INSTITUCIONAL`).
  * **Acción:** `ESAVI_INSTITUCIONAL` llena la Matriz de Riesgo durante la reunión para determinar el nivel de riesgo.
  * **Notificación:** El `SECRETARIADO` recibe una alerta informativa de que se ha iniciado formalmente la investigación del caso.
* **Fase 3 (Asignación del ERR):**
  * **Agendamiento y Acción:** `ESAVI_INSTITUCIONAL` selecciona a los miembros del Equipo de Respuesta Rápida (ERR) en el módulo de Asignación y convoca una reunión de lineamientos, dejando la agenda registrada en el sistema.
  * **Notificación:** Los usuarios designados para el ERR reciben una alerta de asignación y, a partir de ese momento, el sistema les da acceso de lectura a la información consolidada del caso.
* **Fase 4 (Investigación de Campo):**
  * **Acción:** Llenado en terreno de los Anexos V (Puesto), VI (Comunitario), VII (Clínico) y III (Logística) por los responsables correspondientes del ERR.
  * **Notificación:** Una vez que todos los anexos requeridos están marcados como "completados", se envía una notificación automática al `ESAVI_INSTITUCIONAL`.
* **Fase 5 (Control de Calidad y Revisión):**
  * **Revisión Primaria:** `ESAVI_INSTITUCIONAL` revisa los anexos. 
    * *Si hay errores:* Señala en el sistema qué anexo(s) tienen observaciones (esto notifica de regreso al ERR). 
    * *Si todo está correcto:* Aprueba y envía al Secretariado.
  * **Revisión Secundaria:** `SECRETARIADO` recibe notificación de que el caso está listo para su revisión. Si encuentra observaciones, el sistema le permite regresar el expediente a `ESAVI_INSTITUCIONAL`.
* **Fase 6 (Cierre y Dictamen):**
  * **Agendamiento:** `ESAVI_INSTITUCIONAL` convoca una reunión de cierre primero con el Equipo Coordinador y, posteriormente, con el `SECRETARIADO`.
  * **Acción:** Si todo está en orden, el `SECRETARIADO` asigna/habilita el caso para ser presentado ante el `COMITE_EXTERNO`.
